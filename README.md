# Электронный кадровый резерв — прототип с сохранением данных

Небольшое full-stack приложение: фронтенд (тот же интерфейс, что был в демо-артефакте,
плюс отдельная страница управления ролями) + backend на Node.js/Express + хранение
данных в файле `data/db.json` на диске. Никаких внешних баз данных не требуется —
всё работает "из коробки".

## Что внутри

```
kr-app/
  server.js       — Express-сервер, отдаёт API и статику фронтенда
  db.js           — слой хранения данных (чтение/запись data/db.json)
  columns.js      — единое описание столбцов, должностей и ролей по умолчанию
  public/
    index.html    — страница реестра резервистов (таблица, виджеты, фильтры)
    roles.html    — страница "Роли и доступы" (создание ролей, настройка видимости полей)
    common.css    — общие стили: кнопки, модалки, навигация, индикатор сохранения
    common.js     — общие функции: запросы к API, мелкие хелперы форматирования
  data/
    db.json       — файл с данными (создаётся автоматически при первом запуске)
```

Как это устроено: каждая страница при загрузке запрашивает `GET /api/meta`
(описание столбцов/должностей) и `GET /api/state` (текущие данные — резервисты,
общий список, роли), а любое изменение — редактирование ячейки, добавление
сотрудника, удаление, создание/правка роли — отправляется на сервер
(`PATCH/POST/DELETE /api/...`), сервер сохраняет изменения в `data/db.json` и
возвращает актуальное состояние целиком. В шапке каждой страницы есть индикатор
"Сохранено / Сохранение… / Не сохранено" — по нему сразу видно, дошли ли
изменения до сервера.

Переключатель "Смотреть как: …" в реестре — это чисто фронтовая имитация входа
под ролью, без настоящей авторизации: сервер не проверяет права на конкретные
PATCH-запросы, только оформляет то, что фронт присылает. Для демонстрации
логики коллегам этого достаточно; для боевого использования с реальными
данными понадобится настоящая проверка прав на сервере.

## Стресс-тест на большом объёме данных

По умолчанию при первом запуске создаётся 10 куратированных демо-строк. Если нужно
проверить, как интерфейс ведёт себя на тысячах сотрудников (фильтры, пагинация,
скорость сохранения), задайте переменную окружения `SEED_ROW_COUNT` (например, `5000`)
**перед тем**, как база создаётся с нуля — на уже существующий `data/db.json` это не
влияет, нужно сначала его сбросить (см. раздел про деплой на Railway — там же описан
сброс через Volume → Wipe volume).

Первые 10 строк при этом остаются теми же куратированными, а сверху дописывается
`SEED_ROW_COUNT - 10` случайно сгенерированных: даты — в диапазоне 01.01.2025–01.08.2026,
выпадающие списки — случайно из допустимых значений, часть нередактируемых полей
(готовность к релокации, релокация, мотивация, магазин, текущая должность) — тоже с
вариативностью. «Потенциальная должность» / «Обучение в кадровый резерв» / «Дата HARD»
циклично используют уже существующие заготовленные наборы, а не придумывают новые —
там более сложная связанная логика, которую нежелательно трогать генератором.

Учтите: при большом объёме файл `data/db.json` на диске становится заметно крупнее
(при 5000 строк — около 8 МБ), и каждое отдельное сохранение ячейки чуть медленнее
(на тесте — около 150 мс вместо десятков мс на маленькой базе), потому что сервер
пока перезаписывает файл базы целиком при любом изменении.

## Запуск локально

Понадобится [Node.js](https://nodejs.org/) версии 18 или новее (проверить: `node -v`).

```bash
cd kr-app
npm install
npm start
```

Откройте в браузере **http://localhost:3000** — готово. Данные сохраняются в
`data/db.json` и переживут перезапуск сервера и перезагрузку компьютера.

Чтобы сбросить данные к исходному демо-набору — остановите сервер и удалите
папку `data`, при следующем запуске она создастся заново с демо-данными.

Если несколько человек в офисе в одной сети хотят открыть один и тот же
запущенный экземпляр — можно зайти по IP-адресу компьютера, на котором
запущен сервер (например `http://192.168.1.25:3000`), вместо localhost.
Все увидят и будут редактировать одни и те же данные.

## Деплой на Railway (чтобы не запускать локально вообще)

1. Зарегистрируйтесь на [railway.com](https://railway.com) и создайте новый проект —
   можно из GitHub-репозитория (залейте туда папку `kr-app`) или через Railway CLI
   прямо из этой папки (`railway up`).
2. Railway сам определит, что это Node.js-приложение (по `package.json`) и
   выполнит `npm install` + `npm start`.
3. **Важно — постоянное хранилище.** Без этого шага данные будут исчезать при
   каждом передеплое, потому что файловая система Railway по умолчанию
   временная. Добавьте Volume: нажмите `Ctrl+K` (на Mac `⌘+K`) и введите
   «volume» в командной панели, либо кликните правой кнопкой мыши по
   пустому месту канваса проекта — появится пункт создания Volume.
   Прикрепите его к сервису с вашим приложением и укажите путь монтирования
   `/data`.
4. В **Variables** добавьте переменную `DATA_DIR` со значением `/data`
   (тем же путём, что указали при создании volume).
5. Deploy. Railway выдаст публичный URL вида `your-app.up.railway.app` —
   это и есть готовая ссылка, которую можно скидывать коллегам.

Без шага 3–4 приложение тоже запустится и будет работать, но данные будут
жить только до следующего деплоя — для демо-показа разово этого достаточно,
для постоянного использования нужен volume.

## Дальнейшие шаги к "настоящему" продукту

Этот прототип уже решает главную задачу — данные не теряются и с ними можно
работать через браузер. Но прежде чем предлагать его как замену Excel-файлу
на боевых данных сотрудников, стоит обсудить с ИБ/комплаенсом:

- аутентификацию (сейчас доступ к приложению не защищён — открыть его может
  кто угодно, у кого есть ссылка);
- миграцию с файлового хранилища на полноценную БД (Postgres) — для
  прототипа JSON-файла достаточно, но при росте числа резервистов и
  одновременных правок это станет узким местом;
- журнал изменений по каждой строке (кто и когда поменял поле) —
  сейчас изменения просто перезаписывают значение;
- интеграцию с реальными источниками "автоматических" полей (СМскилл и
  другие системы) вместо ручного ввода при добавлении сотрудника.
